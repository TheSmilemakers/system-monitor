Design Revamp Plan

system-monitor · prepared 25/09/2026 by Kai · grounded in the current code (src/app/page.tsx, src/lib/schemas.ts, src/lib/probe.ts, the four API routes) and in probes verified on this Mac today

The idea in one line. Turn the dashboard into a bench instrument: a 1980s test-bench and control-room language (vector scopes, LED bar meters, annunciator lamps, seven-segment readouts) built with 2026 craft (variable fonts, oklch colour, springs, translucent layers), where every process can explain itself and every change to the machine is logged and judged.

Three workstreams. Visual identity ("Phosphor"), richer information (a process inspector with explainers and investigation tools), and constant security monitoring (baseline, drift, posture lamps, a timeline). They ship in five phases over roughly six to eight weeks of one engineer's time; phase A is usable on its own.

The rule that keeps it tasteful. The 80s lives in the instruments, not the wallpaper. No scanlines, no boot screens, no glitch loops by default. One memorable element, the live vector scope, and everything around it quiet.

1. Where the product is today

What works. The data pipeline is sound: argv-only probes with typed outcomes, a rolling five-minute history, sustained-load alerts, a loopback-only trust boundary, and safe kill and cleanup actions. The page already has a terminal temperament, so the direction below is an evolution, not a rewrite.

What holds it back.

  • It is a readout, not an instrument. Numbers are shown; nothing is explained. A process is a short name, a PID and three numbers. There is no way to ask "what is this and should I care?"
  • Flat information architecture. Scan, Cleanup and Privacy are on-demand panels that appear mid-page; there is no place for history, events or posture.
  • Collected but hidden: full command paths are stripped in sampler.ts:94-97; alert duration is shown only in the banner; connections are computed in the privacy scan but never joined to the process rows.
  • Visual system is generic: neutral oklch greys, status colours as ad-hoc Tailwind classes, the tooltip and progress primitives unused, no light mode despite tokens for one.
  • Nothing is remembered between runs. Every launch starts from zero, so "new since yesterday" cannot exist.

2. Design direction: "Phosphor"

Concept

The machine is a signal and the app is the bench it is probed on. The reference world is Tektronix scopes, HP bench meters, airliner annunciator panels, the Vectrex, Trinitron menus and Braun's radio faces: instruments built to be read at a glance for eight hours a shift. That world is monochrome phosphor with one or two alarm colours, discrete segments rather than smooth gradients, and typography engraved on bezels. It maps unusually well onto a security monitor: posture is a row of lamps, load is a meter, events are a chart recorder.

What we take from now: variable fonts with real tabular numerals, oklch colour so the phosphor hues survive light mode, translucent inspector layers, spring motion that can be interrupted, and accessibility as a floor.

Typography

  • Geist Mono stays for every data cell, with font-variant-numeric: tabular-nums and size-specific tracking (+0.01em at 11px, 0 at 13px).
  • Geist Sans for prose: explainers, recommendations, empty and error states. Line length under 70 characters in the inspector.
  • Chakra Petch (SIL licence, self-hosted, so the CSP stays font-src 'self') for the few display moments: panel titles engraved on bezels and the four vital numerals. Squared terminals and a slight forward lean carry the era without cosplay.
  • DSEG7 (SIL) seven-segment numerals appear only inside the four vitals and only at retro level 1 or higher. Segment fonts are hard to read at small sizes, so never below 28px and always with a text alternative.

  • Annunciator strip across the top: security posture as labelled lamps. Lit phosphor = good, amber = attention, alarm = failing, dim = unknown or not yet checked. Click a lamp to open its explainer.
  • Vitals rail on the left: four instruments, each a numeral, a 10-segment LED meter, and the user/sys or wired/compressor breakdown beneath. Vertical stacking reads like a rack.
  • Vector scope in the centre: the one bold element. Four traces (CPU, memory, network bytes, disk activity) over five minutes on a shared phosphor grid, drawn on canvas with afterglow decay. Alerts are marked as ticks on the time axis, not as banners.
  • Workbench tabs below: Processes, Network, Persistence, Permissions, Timeline. The table is the workhorse and keeps most of the width.
  • Inspector on the right: a translucent drawer that slides from the right on a critically damped spring and dismisses the same way. On narrow screens it becomes a bottom sheet with 1:1 drag and momentum projection.
  • Alignment: everything left-aligned to a 12-column grid; numerals right-aligned in cells. Mobile collapses to rail, scope at 120px, then tabs.

Motion and sound

  • Springs, damping 1.0, response 0.3 for the inspector and tab changes; damping 0.8 only after a flick on the mobile sheet. Reduced motion swaps every spring for a 150 ms cross-fade.
  • Trace afterglow is the only ambient motion and it is data, not decoration. It stops when the tab is hidden (the polling hook already pauses).
  • A critical alert triggers one 300 ms horizontal "sync loss" bar across the scope, once, never looping. An amber warning does not animate at all.
  • Sound is off by default. Optional single tick on a new Timeline event, generated with the Web Audio API so nothing is fetched.

Retro intensity control

A three-position switch in the header, persisted locally, applied as data-retro="0|1|2" on the root so it is one attribute for CSS to key from.

Self-critique against the generic defaults

The near-black-plus-one-acid-accent look is a known generated-page tell, and the current UI is already close to it. The plan avoids it in three ways: the base is ivory-on-tube with a warm cast rather than white on #111; the palette has a dominant signal hue plus three functional hues with strict jobs, not one accent used for everything; and the memorable element is a working instrument (the scope) rather than a gradient. The light "daylight lab" theme is a first-class mode so the product does not depend on darkness for its identity. No eyebrow labels, no middle-dot meta strings, no arrows on buttons.

4. Richer information: the inspector

Clicking any process row (or pressing i) opens the inspector. It answers four questions in order: who is this, what does it do, what is it doing right now, and what can I do about it.

4.1 Identity (who is this)

The identity header is the badge: name, publisher, and one of five trust states rendered as a lamp: Apple system, Signed and notarised, Signed, Ad-hoc or unsigned, Unsigned and quarantined. This state also becomes a column and a filter in the table.

4.2 Explainer (what does it do)

Three layers, all offline and instant, so the answer is always present:

  1. Apple's own man pages. This Mac ships 838 section-8 pages. man -w name then the DESCRIPTION paragraph gives, for example, "fileproviderd is the daemon controlling the interaction between extensions and filecoordinationd." Zero maintenance and authoritative.
  2. A curated knowledge base (JSON in the repo, around 250 entries at launch) for what man pages do not say: plain-English purpose, normal CPU and memory range, why it spikes, whether it is safe to kill, and what to check if it misbehaves. Entries for the usual suspects: mdworker_shared, WindowServer, kernel_task, bird, cloudd, trustd, nsurlsessiond, coreaudiod, corespotlightd, Electron helpers, browser renderers.
  3. Heuristics for anything unknown: publisher and bundle from the signature, app name from the enclosing .app, Electron or Chromium helper detection from the argument list, "renderer of Google Chrome" from the parent chain, and a frank "No description available" with the path and publisher rather than a guess.

An optional fourth layer, off by default and clearly labelled: ask a model. It sends only name, path, publisher and parent chain, never arguments or hostnames, and the response is cached. Given the product's privacy stance, this stays opt-in per session.

4.3 Live behaviour (what is it doing now)

  • Per-process CPU and memory trace over the last five minutes, keyed by PID plus start time so PID reuse cannot splice histories. Requires a ring buffer per process in the sampler; cost is negligible at 1,000 processes.
  • Energy impact from top -stats pid,power, threads, and open file and socket counts from lsof -p on demand.
  • Network: its connections joined from the machine-wide lsof -iTCP listing (75 ms for 122 connections today), each resolved, tracker-matched with the existing map, and marked "new destination" if not in the baseline.
  • Alert context: how long it has been over threshold, in the row and in the inspector, not only in a banner.

5.3 The Timeline

A chart-recorder view: time runs downward, one pen colour per category, each event a row with severity, subject, what changed, and a one-line judgement from the rule table. Events link to the inspector. Filters mirror the table's. Retention is local and configurable (default 30 days, SQLite via Bun's built-in driver).

5.4 Notifications and the mini window

  • Alarm events post a macOS notification through osascript's display notification, deduplicated per subject for 10 minutes.
  • The existing Desktop launcher becomes useful all day: a /mini route, 320 × 120, showing the lamps, one meter, and the last event, opened in a small window. This is the constant-monitor surface.
  • A daily shift report (the printout) summarises events, new software, new destinations, and posture changes.

5.5 Rules for staying trustworthy

  • Every probe stays argv-based with a timeout and a typed outcome; the annunciator shows "unknown" rather than guessing when a probe is denied.
  • Nothing leaves the machine unless the user opts in per feature, and the opt-in states what is sent.
  • Judgements are explainable: each event shows the rule that fired and how to silence it for that subject.
  • Destructive actions keep confirmation; suspend is offered before kill.
  • Alarm colour appears in one place at a time; two simultaneous alarms become a count on the lamp, not two red banners.

8. Technical notes

  • Tailwind 4 tokens via @theme; components keep Base UI primitives. Status colours move out of components into the four functional hues.
  • Scope rendering on a 2D canvas: draw each frame over a translucent tube-coloured fill (alpha 0.12) to get afterglow for free; four paths, no per-point DOM. Text equivalent updated per poll for screen readers, as the sparklines do now.
  • Streaming: the Timeline uses a streamed route handler (server-sent events on the Node runtime) so events appear without a poll; the vitals keep the existing polling hook.
  • Persistence: baseline and events in SQLite under Application Support via bun:sqlite; nothing in the repo directory.
  • Caching: signature and man-page lookups keyed by path with TTLs; a bounded pool (the existing pool.ts) keeps concurrent codesign calls at four.
  • CSP unchanged: fonts self-hosted, no external requests, canvas needs nothing new.
  • Accessibility floor: every instrument has a text equivalent; colour is never the only channel (lamps carry labels and shapes); visible focus rings in phosphor; all three reduced-preference media queries honoured; contrast figures in section 2.
  • Testing: each new parser (codesign output, man DESCRIPTION, lsof rows, scutil dns, sfltool) gets fixture-based unit tests; the drift rules get table-driven tests; the inspector gets a happy-dom render test.

9. Interaction and motion specification

This section applies Apple's fluid-interface principles (Designing Fluid Interfaces, WWDC 2018; Principles of Great Design, WWDC 2026) to every interactive surface in the plan. The through-line: motion starts from the current on-screen value, inherits the user's velocity, projects momentum forward, and can be grabbed and reversed at any instant. Section 2's "Motion and sound" notes are superseded by the values here.

9.1 Response: nothing waits for release

  • Every row, lamp, tab and button changes state on pointerdown, not on click. Rows lift to the bezel tone in under 16 ms; the kill and suspend controls show their pressed state instantly and commit on release, with cancel-by-dragging-away.
  • The polling hook's data arrives every 5 s, but interaction never waits on it. Opening the inspector renders the identity and explainer from cache immediately and fills live behaviour when the next sample lands, with a text "sampling" state rather than a spinner.
  • Audit list for the build: no debounce on the filter box above 50 ms, no artificial delay before the command palette opens, no transition-end waits before the inspector accepts input.

9.2 Direct manipulation and interruptibility

Implementation rules: Pointer Events with setPointerCapture; keep the last four positions with timestamps for release velocity; decompose the sheet's drag into independent X and Y springs; never lock input during a transition; animate transform and opacity only, with will-change set on pointer-down and cleared on settle.

// Inspector opened by click or keyboard: critically damped
animate(drawer, { x: 0 }, { type: "spring", bounce: 0, duration: 0.3 });

// Inspector released after a flick: hand off the pointer's velocity, allow a little overshoot
animate(drawer, { x: target },
  { type: "spring", bounce: 0.2, duration: 0.3, velocity: releaseVelocityPx });

// Where the flick will land, Apple's projection (deceleration 0.998 for scroll feel)
const project = (v, d = 0.998) => (v / 1000) * d / (1 - d);
const detent = nearestDetent(currentY + project(releaseVelocityPx));

// Rubber-band beyond the top detent
const band = (over, dim, k = 0.55) => (over * dim * k) / (dim + k * Math.abs(over));

9.4 Spatial consistency

  • The inspector enters from the right and leaves to the right; the sheet enters from the bottom and leaves to the bottom. Never in from one edge and out another.
  • Popovers and the command palette set transform-origin to the control that opened them; the lamp explainer grows out of its lamp.
  • Reversible transitions mirror their easing: the tab pan uses inverse cubic-bézier control points in each direction.
  • Where am I, where can I go, what is here, how do I get out: the workbench tabs answer the first two, the inspector header answers the third, and Escape or a swipe answers the fourth from every state. No view traps focus without a visible exit.

9.5 Materials and depth

  • Two materials only. Bezel: opaque, matte, for the vitals rail and table chrome. Glass: backdrop-filter: blur(20px) saturate(160%) over 72% tube colour, for the inspector, the command palette and the sticky header, with a 1 px lighter top edge so the material reads as catching light.
  • Glass never stacks on glass: the palette opening over the inspector dims the inspector to bezel first.
  • The inspector is a parallel panel, not a modal: no scrim, content stays live underneath, the table keeps updating. Kill confirmation is the one modal task and pairs a scrim with a slight push-back of the page.
  • Vibrancy: text over glass uses ivory at full opacity and weight 500 with +0.01em tracking; colour lives on the solid bezel, never on the glass foreground.
  • Scroll edges: the table's sticky header has no hard rule; a 12 px gradient mask fades content into the glass where they overlap.

9.7 Typography discipline

  • Tracking is size-specific: the four vital numerals at 40 px use -0.02em, panel titles at 15 px use 0, table data at 12 px uses +0.01em, captions at 11 px use +0.015em. One fixed value would be wrong somewhere.
  • Leading tracks size inversely: 1.05 on numerals, 1.3 on table rows, 1.5 on explainer prose.
  • Hierarchy from weight plus size plus leading as a set; emphasis by weight (500 against 400), never by colour alone.
  • Geist stays the body face because it ships tabular figures and optical tuning; Chakra Petch and DSEG7 appear only where section 2 allows, and DSEG7 is never below 28 px.

9.8 Feedback and sound

  • Four kinds, each with one treatment: status (lamps, meters), completion ("Suspended fileproviderd" in the live region and on the row, same words as the button), warning (amber caption before the threshold is crossed, for example "swap rising"), error (inline on the control that failed, with the reason and the fix).
  • The optional tick fires on the same frame as the Timeline row appears; if audio cannot be scheduled on that frame, it is dropped rather than late.
  • Confirmation only for kill and cleanup, which are destructive and irreversible. Suspend, watch, renice and reveal act immediately and offer undo in the live region for 8 s.

9.9 The eight principles as decisions for this product

PrincipleDecision
PurposeParked ideas stay parked. The isometric city, skins and boot screen were cut because they spend attention without answering a question.
AgencySuspend before kill; undo on every non-destructive action; rules can be silenced per subject; the retro switch and light theme are the user's call.
ResponsibilityNothing leaves the machine by default. The model explainer is opt-in per session and names exactly what it sends. Probes are read-only and argv-based. An unknown publisher is stated as unknown, not judged as malicious.
FamiliarityLamps, meters and scopes are metaphors people already read; kill and cleanup keep their names and positions from the current app; Escape closes, Cmd-K opens, as everywhere on the Mac.
FlexibilityDesktop gets density and keyboard; touch gets the sheet and swipes; the mini window serves the glance case; columns can be hidden and reordered.
SimplicityThe common path (glance at lamps and scope, find the hog, inspect, suspend) is one level deep. Network, Persistence and Permissions are a level down. Adding the explainer is the kind of context that simplifies.
CraftEvery spring value, tracking value and colour role above is a defensible choice. Motion is reviewed frame by frame before phase B ships.
DelightThe emotion is calm confidence: the machine is understood and under control. The instruments deliver it; nothing is added on top.

9.10 Process for phases A and B

  • Prototype the inspector drawer and sheet interactively before styling anything; an interactive demo sets the bar the final build must meet.
  • Design the scope and its interactions together: the time axis is both the display and the scrubber, so neither is finished until both are.
  • Review motion at quarter speed with fresh eyes; check every interruption path by grabbing mid-flight.
